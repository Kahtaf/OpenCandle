## Requirements
### Requirement: Shared Doctor Report
The system SHALL provide a structured OpenCandle doctor report that is generated by shared server-side code and consumed by both CLI and GUI diagnostics surfaces. The report SHALL include a schema version, overall status, section statuses, individual checks, severity, capability impact, checked timestamp, user-facing summary, and remediation guidance.

#### Scenario: Report contains overall and section status
- **WHEN** the doctor report is generated
- **THEN** the report includes an overall status derived from its checks
- **AND** each section includes its own status and list of checks

#### Scenario: Report contains a schema version
- **WHEN** the doctor report is generated for CLI JSON output or GUI rendering
- **THEN** the report includes a top-level schema version
- **AND** consumers can use the schema version to handle future report shape changes

#### Scenario: CLI and GUI consume the same report model
- **WHEN** the CLI renders `opencandle doctor` and the GUI renders the Diagnostics page
- **THEN** both surfaces use the same structured doctor report data
- **AND** neither surface re-implements provider, runtime, path, or session health logic independently

### Requirement: Diagnostic Severity Model
The doctor report SHALL classify each check as `pass`, `warn`, `fail`, `skip`, or `unknown`. Each check SHALL identify whether the affected capability is core or optional. The report SHALL distinguish blocked core functionality from degraded optional coverage.

#### Scenario: Core runtime failure blocks readiness
- **WHEN** Node is unsupported or the native SQLite binding cannot load
- **THEN** the related check is classified as `fail`
- **AND** the overall report status reflects that OpenCandle is blocked until remediation is completed

#### Scenario: Optional provider missing is degraded coverage
- **WHEN** an optional enrichment provider such as Finnhub, Brave, Exa, Reddit, or Twitter/X is missing
- **THEN** the related check is classified as `warn` or `unknown`
- **AND** the report explains which capability is degraded without marking all of OpenCandle as unusable

#### Scenario: Core failure makes overall status blocked
- **WHEN** one or more core checks are classified as `fail`
- **THEN** the overall report status is blocked
- **AND** the summary identifies the blocking remediation

#### Scenario: Non-blocking issues make overall status degraded
- **WHEN** no core checks fail but any optional check is `fail` or any core or optional check is `warn` or `unknown`
- **THEN** the overall report status is degraded
- **AND** the summary identifies the affected capability without claiming OpenCandle is fully unusable

#### Scenario: Passing core checks make overall status ready
- **WHEN** all core checks pass and optional checks are pass or intentionally skipped
- **THEN** the overall report status is ready

### Requirement: Runtime and Local State Checks
The doctor report SHALL include checks for OpenCandle version, Node version support, native `better-sqlite3` readiness, current working directory, resolved `OPENCANDLE_HOME`, config file presence and parse status, onboarding state, SQLite state store availability, sentiment history store availability, and Pi agent directory location.

#### Scenario: OpenCandle home is reported
- **WHEN** `OPENCANDLE_HOME` is unset
- **THEN** the report shows the default resolved OpenCandle home path
- **AND** marks it as the default location

#### Scenario: OpenCandle home is overridden
- **WHEN** `OPENCANDLE_HOME` is set
- **THEN** the report shows the resolved override path
- **AND** marks the source as environment-provided

#### Scenario: Config file is invalid
- **WHEN** `$OPENCANDLE_HOME/config.json` exists but cannot be parsed as valid JSON
- **THEN** the config check is classified as `fail`
- **AND** the remediation explains how to repair or remove the invalid config file

### Requirement: Model Readiness Checks
The doctor report SHALL include model readiness separate from market-data provider readiness. The model section SHALL indicate whether chat is ready, whether a model must be selected, or whether model authentication must be connected.

#### Scenario: No model credentials are available
- **WHEN** no usable Pi model credentials are configured
- **THEN** the model readiness check reports `connect_auth`
- **AND** the check is classified as a core `fail`
- **AND** the overall report status is blocked
- **AND** the remediation directs the user to run `/setup` or use the GUI model setup panel

#### Scenario: Model credentials exist but no active model is selected
- **WHEN** at least one model provider is available but no active model is selected
- **THEN** the model readiness check reports `select_model`
- **AND** the check is classified as a core `fail`
- **AND** the overall report status is blocked
- **AND** the remediation directs the user to select an available model

### Requirement: Provider Capability Diagnostics
The doctor report SHALL group data provider diagnostics by capability category and provider tier. The report SHALL show provider display name, category, tier, credential or install source, current status, capability impact, and remediation.

#### Scenario: API-key provider source is reported without exposing secrets
- **WHEN** an API-key provider is configured by environment variable or config file
- **THEN** the report shows the credential source
- **AND** the report does not include the secret value

#### Scenario: Yahoo reachability is reported as core market readiness
- **WHEN** the Yahoo public HTTP probe succeeds
- **THEN** the market data section reports Yahoo Finance as reachable
- **AND** simple quote and market-data workflows are represented as available

### Requirement: External Tool Install and Session Separation
The doctor report SHALL represent external-tool binary readiness separately from browser-session readiness for providers that require both, including Reddit and Twitter/X.

#### Scenario: Twitter binary installed but session unchecked
- **WHEN** `twitter-cli` is installed and session checks were not requested
- **THEN** the report shows the Twitter/X binary as installed
- **AND** shows the Twitter/X browser session as `unknown` or `not checked`
- **AND** explains how to run the session check explicitly

#### Scenario: Reddit binary installed but session missing
- **WHEN** `rdt-cli` is installed and an explicit session check reports that Reddit is not authenticated
- **THEN** the report shows the Reddit binary as installed
- **AND** shows the Reddit browser session as `warn` for degraded optional sentiment coverage
- **AND** does not make the overall report status blocked
- **AND** the remediation includes `rdt login`

#### Scenario: External tool missing
- **WHEN** `twitter-cli` or `rdt-cli` is missing
- **THEN** the report includes the exact `uv tool install ...` command for that provider

### Requirement: Privacy-Aware Session Checks
Browser-session checks SHALL be opt-in from both CLI and GUI surfaces. The system SHALL warn that these checks may read browser cookies or trigger platform permission prompts before running them. Any output from session probes SHALL be redacted before display.

#### Scenario: Default doctor does not run browser-session probes
- **WHEN** the user runs `opencandle doctor` without a session-check flag
- **THEN** the command does not run Reddit or Twitter/X browser-session probes
- **AND** the report marks browser-session readiness as not checked

#### Scenario: Explicit session check runs browser probes
- **WHEN** the user runs `opencandle doctor --sessions` or triggers the GUI session-check action
- **THEN** the system runs Reddit and Twitter/X session probes
- **AND** the report includes ready, missing, stale, or error status for each browser session

#### Scenario: Full doctor does not imply browser-session consent
- **WHEN** the user runs `opencandle doctor --full` without `--sessions`
- **THEN** the command does not run Reddit or Twitter/X browser-session probes
- **AND** the report marks browser-session readiness as not checked

#### Scenario: Sensitive output is redacted
- **WHEN** a session probe returns cookie, token, session, credential path, or similar sensitive output
- **THEN** the displayed CLI and GUI report redacts the sensitive value

### Requirement: CLI Doctor Surface
The CLI SHALL render the shared doctor report as concise human-readable terminal output by default and SHALL support JSON output for automation. The CLI SHALL preserve the existing provider re-enable behavior.

#### Scenario: Human-readable doctor output
- **WHEN** the user runs `opencandle doctor`
- **THEN** the CLI prints a summary followed by grouped diagnostic sections
- **AND** each failed or degraded check includes concise remediation

#### Scenario: JSON doctor output
- **WHEN** the user runs `opencandle doctor --json`
- **THEN** the CLI prints the structured doctor report as JSON
- **AND** the JSON includes the same checks and statuses as the human-readable report
- **AND** the JSON includes the top-level schema version

#### Scenario: Provider re-enable remains available
- **WHEN** the user runs `opencandle doctor --enable reddit`
- **THEN** the command clears the skipped onboarding state for Reddit
- **AND** the report reflects the re-enabled provider state

### Requirement: GUI Diagnostics Surface
The GUI SHALL provide a first-class Diagnostics surface rendered as the Diagnostics section of the Settings page at `/settings/diagnostics`, rendering the shared doctor report. The legacy `/diagnostics` path SHALL continue to resolve to this surface. The surface SHALL summarize health and link to remediation actions; provider remediation SHALL navigate to Settings → Data providers.

#### Scenario: Diagnostics page shows whole-system status
- **WHEN** the user opens the Diagnostics section under Settings
- **THEN** the page shows runtime, state, model, provider, sentiment, session, and GUI status sections
- **AND** the status values match the shared doctor report

#### Scenario: Legacy diagnostics route resolves
- **WHEN** the user opens `/diagnostics` directly
- **THEN** the Diagnostics content renders as the active Settings section at `/settings/diagnostics`

#### Scenario: Provider remediation opens provider setup
- **WHEN** a provider check has a remediation requiring key entry, install command, or session check
- **THEN** the GUI offers an action that navigates to Settings → Data providers focused on that provider

#### Scenario: Model remediation opens model setup
- **WHEN** the model readiness section reports `connect_auth` or `select_model`
- **THEN** the GUI offers an action that navigates to Settings → Model

### Requirement: GUI Runtime Status
The doctor report SHALL include GUI-specific status when requested by the GUI or full CLI diagnostics. GUI status SHALL report WebSocket/HTTP connectivity, writer or follower role, configured host and port, and whether the GUI server health endpoint is reachable.

#### Scenario: CLI discovers GUI reachability target
- **WHEN** CLI diagnostics include GUI reachability
- **THEN** the check probes the configured GUI host and port when available
- **AND** falls back to the documented local default when no configured value exists

#### Scenario: GUI is running as writer
- **WHEN** the GUI health endpoint is reachable and reports writer role
- **THEN** the GUI status check reports that chat and setup mutations can be performed by this process

#### Scenario: GUI is running as follower
- **WHEN** the GUI health endpoint is reachable and reports follower role
- **THEN** the GUI status check warns that write actions may be unavailable in that process

#### Scenario: GUI is not running
- **WHEN** CLI diagnostics check GUI reachability and no GUI server is listening
- **THEN** the GUI status check reports not running
- **AND** the check does not make the overall CLI health fail

### Requirement: Remediation-Oriented Output
Every failed, warning, or unknown actionable check SHALL include remediation text or an explicit explanation that no action is required.

#### Scenario: Missing external tool includes install command
- **WHEN** an external tool check is missing
- **THEN** the remediation includes the exact install command from the provider registry

#### Scenario: Unsupported Node includes version guidance
- **WHEN** the Node version is unsupported
- **THEN** the remediation includes the supported Node range and dependency reinstall or rebuild guidance

#### Scenario: Optional check not run explains how to run it
- **WHEN** a browser-session check is not run by default
- **THEN** the remediation explains how to run the opt-in session diagnostics
