## Disclaimer-surface mechanism decision

**Initial choice**: option 2 (custom display message via `pi.sendMessage({customType, display: true, content})`) emitted from a `turn_end` handler. Refined after a live-run revealed a hard constraint in Pi's API.

**Constraint discovered during implementation**: Pi's `convertToLlm` (in `node_modules/@earendil-works/pi-coding-agent/dist/core/messages.js`, `case "custom"`) maps every `CustomMessage` sent via `pi.sendMessage` to an LLM `role: "user"` message, regardless of `customType` or `display`. There is no `excludeFromContext` flag on `CustomMessage` (that field only exists on `BashExecutionMessage`), no post-response text-mutation hook, and no "render-in-transcript-but-skip-LLM" channel. A live run against Gemini 2.5 Flash with the naive per-turn `sendMessage` confirmed the failure mode: after one or two turns, the model sees repeated "`[disclaimer text]`" user messages in history and breaks with "we seem to be stuck in a loop; the user keeps sending the boilerplate disclaimer."

**Final mechanism — hybrid**:
1. **`ctx.ui.setStatus("opencandle-disclaimer", DISCLAIMER_TEXT)`** pinned at `session_start`. The status bar persists for the entire session, visible to the user on every turn, and does NOT enter LLM context at all. This is the primary user-visible channel in interactive TUI mode. Verified via `node_modules/@earendil-works/pi-coding-agent/dist/core/extensions/types.d.ts`: `ExtensionUIContext.setStatus(key: string, text: string | undefined): void`.
2. **`pi.appendEntry("opencandle-disclaimer", {text})`** emitted from a `turn_end` handler, gated on `event.message.role === "assistant" && event.message.stopReason === "stop"` (i.e., only at the final user-visible answer of a turn, not on intermediate tool-use turns). Verified via `session-manager.d.ts`: `CustomEntry` is explicitly documented as "Does NOT participate in LLM context (ignored by `buildSessionContext`)." This gives a per-turn persistent session record for downstream renderers / exporters / harness tests without any LLM-context bleed.

**Why this satisfies the spec**: the spec scenario reads "`user's transcript includes the canonical disclaimer block for that turn (either appended to the response, rendered as a separate transcript entry, or otherwise surfaced such that the user sees it)`." The permanent footer status is "otherwise surfaced such that the user sees it." The hard spec requirement — disclaimer MUST NOT appear in the system-prompt instruction context — is satisfied cleanly: no section of `buildSystemPrompt` / `PromptContextBuilder` contains the disclaimer text any more, and no `sendMessage` path is used (which would have reinjected it as a user-turn message).

**Trade-off accepted**: in non-UI modes (RPC, print, raw harness) the status bar doesn't render, so the disclaimer visibility relies on consumers reading the `opencandle-disclaimer` custom entries from the session file. This is honest — interactive CLI is the primary product surface. The alternative (forcing visibility via `sendMessage`) breaks the agent.

**Disclaimer text constant**: lives as `DISCLAIMER_TEXT` in `src/prompts/disclaimer.ts` so future wording changes are a one-line edit.
