## Context

OpenCandle has two public-facing visual surfaces:

- the local GUI under `gui/web`, built with React, Tailwind tokens, and reusable UI primitives;
- the public homepage/docs site under `website/`, currently generated by `website/build.mjs` into static files for GitHub Pages.

The public site must remain static because it is hosted through GitHub Pages from `website/dist`. The docs must continue to render Markdown sources from `docs/*.md` and selected root project files. The local GUI must remain a local-device app backed by the OpenCandle runtime, session store, WebSocket stream, writer/follower lock, and provider setup state.

The current public site uses a standalone CSS token set and custom HTML/Markdown generation. It visually resembles a marketing/docs site rather than the local GUI and carries parser/maintenance risk because Markdown rendering is implemented by ad hoc string logic.

## Goals / Non-Goals

**Goals:**

- Make the public homepage and docs site look like the main local GUI.
- Keep the public site deployable as static GitHub Pages output from `website/dist`.
- Keep Markdown as the documentation source of truth.
- Share runtime-agnostic tokens and visual primitives between `gui/web` and `website`.
- Prerender public pages to real HTML files for direct links, crawlers, no-JavaScript readability, and current link-check behavior.
- Preserve existing public metadata outputs such as canonical URLs, social cards, JSON-LD, Markdown alternates, `llms.txt`, `llms-full.txt`, `robots.txt`, and `sitemap.xml`.

**Non-Goals:**

- Do not host the local GUI as a public cloud application.
- Do not make the public site depend on local GUI APIs, WebSocket events, writer locks, session data, provider keys, or Pi/OpenCandle runtime state.
- Do not replace Markdown docs with JSX-only documentation.
- Do not require a separate docs hosting service.
- Do not change finance tools, routing, prompts, provider integrations, or GUI runtime behavior beyond consuming shared presentation primitives.

## Decisions

### Decision: Share presentation, not runtime

Create a root `packages/ui` workspace for tokens, logo, and primitive components. The GUI and website both consume that shared presentation layer, while GUI-only containers continue to own local runtime behavior.

Rationale:

- The desired consistency is visual, not operational.
- The GUI's session and stream hooks are intentionally local-only and would fail on GitHub Pages.
- Reusing primitives gives consistency without coupling public pages to local state.

Alternatives considered:

- Deploy the GUI bundle as the public site: rejected because it depends on local APIs and has no useful public runtime.
- Keep duplicating CSS in `website/styles.css`: rejected because drift is the current problem.

The shared UI package must remain import-boundary clean: it can depend on React and small presentation helpers, but it must not import GUI runtime hooks, session state, toast state, local API clients, context-panel state, or feature modules. The first implementation slice should include a boundary assertion or build-time check that fails if shared UI imports from GUI runtime paths.

### Decision: Convert `website/` to a React static-site build

Make `website/` a public-site workspace with a Vite React build plus a Node prerender step. Use React for the public site shell and docs chrome, then prerender each known route to raw HTML during `npm run docs:site:build`. Continue writing output to `website/dist` so the GitHub Pages workflow can upload the same artifact directory.

Rationale:

- The GUI already uses React; React static rendering lets the public site reuse the same component primitives.
- Prerendered HTML preserves direct URLs, crawler visibility, no-JavaScript docs readability, and link-check simplicity.
- GitHub Pages supports build-step output through Actions artifacts, and the repo already has that workflow.

Alternatives considered:

- Use a client-only SPA: rejected because docs pages should be direct static HTML with working links and metadata per page.
- Adopt a full docs framework immediately: rejected as avoidable complexity while the repo already has a small custom static output surface.

The generated HTML files must contain the primary page content, navigation links, headings, and resolved docs links before any client-side JavaScript runs. Hydration may be used for small enhancements, but it must not be required to read docs content or discover public docs links.

Use `@vitejs/plugin-react` for the public-site workspace instead of custom JSX/Babel wiring.

### Decision: Replace the hand-written Markdown renderer with a real Markdown pipeline

Render Markdown through `gray-matter`, `unified`, `remark-parse`, `remark-gfm`, `remark-rehype`, `rehype-slug`, `rehype-autolink-headings`, and `rehype-stringify`. Use AST utilities such as `unist-util-visit` and `mdast-util-to-string` for TOC/heading extraction instead of regex or per-line parsing. Add `shiki` only if the first implementation slice includes static syntax highlighting; otherwise defer it.

Rationale:

- Current manual parsing does not fully cover GitHub-flavored Markdown, nested lists, heading collisions, escaping, code fences, raw HTML behavior, or table edge cases.
- A parser pipeline is easier to validate and extend without repeatedly patching string replacements.
- Plain Markdown remains contributor-friendly and compatible with GitHub rendering.

Alternatives considered:

- MDX: defer until the docs need embedded React components. MDX adds power but also contributor and safety complexity.
- Continue manual parsing: rejected because docs correctness is part of this change.

The migration should remove the old custom parser path rather than leave it as a parallel fallback. In particular, the responsibilities currently handled by functions such as `stripFrontmatter`, `inlineMarkdown`, `renderTable`, `renderMarkdown`, and `slugify` should move to the maintained parser pipeline or small AST transforms. Local-link rewriting and public-page registry logic may remain project-specific, but they should operate on parsed links/metadata rather than broad Markdown string replacements where practical.

### Decision: Preserve existing public artifacts and link shape

The new build must continue emitting:

- `index.html`;
- one HTML page per configured public doc;
- Markdown alternates for public docs;
- `llms.txt` and `llms-full.txt`;
- `robots.txt`;
- `sitemap.xml`;
- per-page JSON-LD structured data;
- copied static assets, favicon, and social image assets.

Rationale:

- These outputs are already part of release and public-doc validation.
- Maintaining URLs limits SEO, crawler, README, and package metadata risk.

The public docs inventory should remain explicit. The current site uses a configured page list rather than walking all of `docs/`; the new build should preserve an explicit public-page registry or an equivalent deny rule for `docs/internal/**` so internal planning files cannot be published accidentally.

### Decision: Split shared CSS from app-only CSS

Move common CSS variables, Tailwind theme mapping, typography defaults, focus treatment, and primitive component styles into a shared layer. Keep app-only rules such as full-viewport height, body overflow lock, chat transcript layout, local drawers, and runtime-specific surfaces in the GUI package.

Rationale:

- The docs site needs normal document scrolling.
- The app needs a fixed-height local workspace.
- Sharing the whole GUI stylesheet would transfer app constraints to docs and create mobile/scrolling regressions.

## Risks / Trade-offs

- Shared package churn could disturb the GUI while improving the site -> Migrate primitives first with no visual behavior change in the GUI, then build the site on top.
- Static React build could accidentally become client-only -> Add build checks that verify generated HTML files contain main content without requiring JavaScript.
- Markdown parser migration could change generated anchors or link targets -> Add focused fixture tests for headings, duplicate headings, tables, code fences, local links, and generated Markdown alternates.
- Adding packages without deleting old code could increase complexity -> Treat the hand-written Markdown/frontmatter renderer as deprecated and remove it once parity tests pass.
- GitHub Pages base-path assumptions could break assets -> Keep absolute/canonical URL generation centralized and test the built `website/dist` through the existing static server.
- MDX pressure could grow after React conversion -> Keep plain Markdown as the default and require a separate decision before allowing MDX in public docs.
- Site design could still drift from the GUI -> Keep shared tokens/primitives as the only allowed source for buttons, cards, badges, logo, keyboard labels, and core shell colors.

## Migration Plan

1. Extract runtime-agnostic GUI primitives and tokens into `packages/ui`.
2. Update the local GUI to consume the shared primitives with no intended visual changes.
3. Add a Vite React static-site workspace under `website/` that can render the homepage and one docs page to `website/dist`.
4. Replace manual Markdown rendering with the maintained Markdown pipeline, port all configured public docs, and delete the old custom parser helpers after parity checks pass.
5. Recreate current metadata outputs, Markdown alternates, `llms` files, robots, sitemap, and copied assets.
6. Rework the public homepage and docs shell to visually match the GUI's app shell and mobile behavior while keeping public calls to action appropriate for a static site.
7. Update validation to cover static build, link checks, generated HTML content, Markdown rendering fixtures, and Browser screenshots for desktop/mobile homepage and docs.
8. Keep `.github/workflows/pages.yml` uploading `website/dist`; only change build internals unless artifact requirements change.

Rollback strategy:

- Keep the existing `website/build.mjs` behavior reachable until the React static build passes output parity and visual checks.
- If the React static build blocks release, revert `docs:site:build` to the previous generator while keeping extracted GUI primitives if they are already stable and independently validated.

## Open Questions

- Should the static site ship any client-side hydration for interactive mobile navigation, or keep navigation fully CSS/HTML?
- Should syntax highlighting be added in the first implementation slice or deferred until after parser migration parity?

## Resolution of open questions

- Mobile navigation shipped as prerendered drawer markup plus a small `website/src/entry-client.jsx` enhancement script that toggles the drawer, focus, overlay close, and Escape close behavior. The site does not hydrate a React nav drawer, and docs content/navigation links remain present in the generated HTML.
- Shiki was deferred from the first slice and remains deferred; no active OpenSpec change currently tracks static syntax highlighting.
- The old `website/build.mjs` markdown pipeline was removed. Searches under `website/` found no remaining `stripFrontmatter`, `inlineMarkdown`, or `renderTable` helpers.
