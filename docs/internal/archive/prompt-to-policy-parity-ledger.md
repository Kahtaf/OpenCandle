# Planning Parity Ledger

This ledger preserves existing product behavior while task-specific obligations move into scoped owners such as evidence plans, policy cards, answer contracts, structured checks, tools, and harness assertions. Treat every row below as existing product behavior until its characterization gate passes. Completion means current behavior is preserved and traceable planning scaffolding exists; it does not require prompt shrinkage.

## No-Regression Rule

No global prompt clause, deterministic router correction, workflow behavior, provider-degradation behavior, or tool-scope rule may be removed, weakened, or made inactive until the matching ledger row has:

- a current owner/source location
- a replacement owner
- characterization prompts or tests
- hard assertions for route, workflow, tools, evidence/provider gaps, and final answer obligations
- baseline report or trace paths
- migration status
- rollback knob

Judge-scored improvement cannot override a failed hard assertion unless `acceptedImprovement` explicitly names the changed assertion and why the behavior is better.

## Status Values

| Status | Meaning |
| --- | --- |
| `legacy_active` | Current prompt, router, workflow, provider, or tool-scope behavior remains active. |
| `observe_only` | Replacement metadata/checks may be recorded but cannot alter prompt, tools, or answers. |
| `dual_run` | Legacy and replacement paths both run for comparison; legacy remains authoritative. |
| `replacement_active` | Replacement path is authoritative after parity passed. |
| `legacy_removed` | Original prompt/rule has been removed after passing gates. |

## Shadow Planning Definition

Shadow planning runs after route validation, deterministic safety-net correction, workflow dispatch selection, and tool-bundle selection. It may add planning metadata, minimal evidence records, capability-gap IDs, policy-card IDs, answer-contract IDs, and observe-only structured-check results. It must not change route kind, workflow, active tool scope, clarification behavior, provider-degradation handling, final-answer text, or prompt-clause ownership unless the row status is `dual_run`, `replacement_active`, or `legacy_removed` with a passing parity gate.

## V1 Completion Gate

V1 is complete when OpenCandle has feature parity with current behavior plus traceable planning scaffolding:

- issue #22 router-boundary tests pass
- prompt-size and no-truncation gates cover production variants
- every prompt-protected behavior below has a ledger row
- planning metadata is present in resolved turn contexts and traces
- non-migrated task families remain observe-only
- one selected migration slice has passing parity before any prompt clause is removed
- rollback knobs are documented for policy-card injection, shadow planning diagnostics, retry-eligibility tracing, and hard tool enforcement

Prompt shrinkage is a later outcome, not the V1 success criterion.
